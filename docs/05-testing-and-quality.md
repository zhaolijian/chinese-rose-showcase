# 05 · 测试与质量：一个人怎么保证"上线的东西是对的"

> 本文只写**做法、数字与结论**，不贴内部测试报告全文。当时的原始报告里带着测试账号、本机路径、环境信息与内部服务器配置，按脱敏要求不随仓库公开；下面出现的数字都注明了记录日期与口径。

---

## 1. 测试策略

### 1.1 分层

| 层级 | 工具 | 覆盖什么 | 谁在什么时候跑 |
|---|---|---|---|
| 单元测试 | Go `testing` / Vitest | 业务规则、工具函数、store、composable、组件渲染 | 每次改动，提交前 |
| 集成测试 | Go `testing` + mock 外部依赖 | UseCase 编排、登录流程、token 缓存与并发 | 每次改动，提交前 |
| 接口 / 冒烟 | 脚本化请求 + 健康检查 | 服务可用性、关键 API 返回、构建产物 | 阶段性 / 上线前 |
| E2E | Playwright（H5 宿主） | 页面主链路、视觉回归、Console 错误 | 功能完成后 / 回归时 |
| 真机验证 | 微信开发者工具 + 真机 | 小程序特有 API（拍照、OCR、相册、登录） | 提审前 / 发版前 |

### 1.2 TDD 的落地方式

我用的不是严格意义上的"红灯 → 绿灯 → 重构"，而是两条约束：

1. **接口先有测试，再写实现**：新增 API / UseCase 时，先写"期望的输入输出与错误分支"的测试，再写实现；ISBN 查询、登录流程、导出接口都是这么做的；
2. **完成定义（DoD）包含测试**：一个需求只有在"有对应测试 + 跑通 + lint 通过"之后才算完成，而不是"代码能编译"就算完。

TDD 在这个项目里的真实收益不是"少写 bug"，而是**强迫我在动手前把接口协议和错误分支想清楚**——尤其是 OCR / LLM 这种外部依赖不稳定的模块，先想清楚失败路径比先写代码重要。

## 2. 后端测试

### 2.1 单元与集成测试

| 类型 | 做法 | 结果（记录日期） |
|---|---|---|
| 单元测试 | 与代码同目录的 `_test.go`，外部依赖用 mock（微信、短信、LLM、仓储） | 按模块统计，整体覆盖率 **35.6%**（2025-09-30 `go test ./... -cover`） |
| 登录模块 | 覆盖双 code 登录（loginCode + phoneCode）、老用户绑定手机号、错误码 40029 / 47001、数据库故障降级 | UseCase 层 **57.5%**、微信 Service 层 **56.0%**、API 层 **24.8%** |
| access_token 缓存 | 缓存命中、过期自动刷新、10 并发只触发 1 次外部请求、失败不缓存 | 通过 |
| 集成测试 | UseCase 编排 + 外部依赖 mock，验证完整调用顺序 | **10/10 通过**（2025-09-30） |
| ISBN 查询 | Mock 模式 + 缓存规范化 + 外部服务降级 | 通过（2025-09-21） |
| 短信登录 | Mock / 真实服务双提供商工厂 + 多级限流（分钟 / 小时 / 天） | 通过（2025-09-21） |
| PDF 导出 | 生成格式、文件魔数、COS 上传与预签名下载 | **4/4 通过**（2025-09-07）：单条笔记约 0.75s；同批测试覆盖了书籍汇总导出的早期接口，该能力未作为最终交付保留 |
| 综合冒烟 | 后端健康、关键 API、前端编译与小程序产物、运行环境指标 | **18/18 通过**（2025-09-27） |

> **诚实结论**：后端整体覆盖率只有 35.6%，**没有达到当时定的 80% 目标**。原因是核心链路开发优先于补齐测试，且 OCR / LLM / COS 这类外部依赖的测试写起来成本高。这是当时记录在案的技术债，不是"忽略不计"。

### 2.2 接口级验证的做法

- 新接口先写一组"正常 / 缺参 / 越权 / 外部依赖失败"的请求用例，跑通后再接前端；
- 涉及第三方（微信、短信、COS、LLM）的接口，一律支持 **Mock 模式**，用环境变量切换——这样在没有外网 / 没有配额时也能跑完整链路；
- 导出、上传这类有文件产物的接口，验证"文件真的能下载 + 格式正确"，而不是只看 HTTP 200；
- 对外错误统一走业务错误码，测试里同时断言"用户看到的提示"和"HTTP 状态码"。

## 3. 前端测试

### 3.1 单元测试（Vitest）

- **范围**：store（Pinia）、composables、工具函数、页面关键逻辑、组件渲染；
- **规模**：当时一次全量运行覆盖 29 个测试文件、233 个用例，耗时约 3 秒（后续测试文件增至 30+ 个）；
- **一次真实的全量结果**（2025-10-02）：**29 个测试文件、233 个用例，229 通过、4 失败**——失败全部集中在登录页，原因是 DOM wrapper 环境与 Vue 响应式在测试环境中的限制，不是业务逻辑错误；
- **后续修复**：之后又集中修了一轮测试环境问题，共 28 个用例（ImageUpload 10 个、add 表单 7 个、login 11 个），其中 3 个因测试框架限制被显式跳过并写明原因；
- **两个关键做法**：
  1. **第三方组件库（uView Plus）的 stub 要写模板，不能只写 `true`**，否则 DOM 选择器永远找不到元素；
  2. **异步组件测试必须统一 flush**：`flushPromises()` + `nextTick()` + 一个宏任务，三者缺一就容易出现"偶发失败"。

### 3.2 E2E（Playwright）

- **宿主**：H5（uni-app 编译到 H5），因为小程序端无法直接跑 Playwright；
- **设备**：`iPhone 13 Pro` 视口（390×844，DPR 3）+ Mobile Chrome 项目；
- **做法**：
  - 页面级 API 用 `page.route` 全部 mock，E2E 不依赖后端环境与真实数据；
  - 截图前禁用所有动画（`animation-duration: 0s`），等图片加载完成，再等 500ms 渲染稳定；
  - `expect(page).toHaveScreenshot(maxDiffPixelRatio: 0.02)` 做视觉回归（允许 2% 像素差异）；
  - 监听 `console.error` 与 `pageerror`，过滤 HMR / DevTools / uni-app / Vue 的框架级噪声后，要求**零关键错误**；
  - 失败自动保留 trace / 截图 / 视频，便于定位。
- **覆盖**：书籍详情页冒烟（关键元素可见、视觉回归、Console 无错误三组用例）；其余 H5 页面以快速脚本 + 手动走查为主，没有全部纳入 Playwright。
- **覆盖率策略**：当时定的是 90/10 分工——H5 自动化尽量覆盖页面级回归（约 90%），小程序端专用能力（拍照、OCR、文件、微信登录）留给真机验证（约 10%）。这是分工目标，不是已达成比例。

### 3.3 真机验证

提审前用手动清单在真机上走一遍：

| 场景 | 验证点 |
|---|---|
| 登录 | 微信一键登录、拒绝授权后的降级、短信验证码登录、token 过期后的 401 处理 |
| 拍照 / OCR | 相机与相册权限、单图 / 多图、框选、识别失败降级、弱网超时 |
| 笔记 | 新建 / 编辑 / 删除（软删除标记）、章节归属、长文滚动 |
| 导图 | 生成、查看缩放、保存相册、删除、生成失败提示 |
| 导出 | PDF / Word / Markdown 生成与下载、中文不乱码 |
| 异常 | 断网、后台切换、重复点击、空数据 |

设备覆盖：少量 iPhone 与 Android 真机 + 微信开发者工具模拟器；**没有做机型矩阵**，这是当时的边界。

## 4. 视觉回归的做法

视觉回归是设计系统落地后最划算的一类测试——页面样式被令牌统一之后，一张截图就能发现"某个页面被改坏了"。

- **基线**：按设备（iPhone 13 Pro 3x）生成基准截图，提交到仓库；
- **阈值**：`maxDiffPixelRatio: 0.02`，允许 2% 像素差异（字体渲染、抗锯齿会导致微小差异）；
- **稳定性**：禁用动画、等待图片加载、固定视口与 DPR；
- **平台注意**：基线截图带平台后缀（darwin），换系统会不匹配——这是 Playwright 的机制，不是测试失败；
- **失败处理**：先看 diff 图确认是"样式回归"还是"渲染差异"，前者修代码、后者更新基线并在提交说明里写原因。

## 5. 质量门槛与提交前检查

一个改动要进入主干，至少满足：

1. `npm run lint`（ESLint）0 error；当时全量是 0 error / 13 warning（都是未使用变量）；
2. `npm run type-check`（vue-tsc）通过；
3. 单测全量通过（失败的用例必须是有记录的跳过，不能静默忽略）；
4. 小程序构建成功、H5 构建成功；
5. 真机清单跑过一遍（涉及端上能力的改动）。

## 6. 踩过的坑与修复

| 问题 | 现象 | 修复方式 |
|---|---|---|
| uView Plus 组件在测试里不可见 | 表单用例全部找不到元素 | 给 `u-input` / `u-form-item` 写带模板的 stub，用组合选择器 `input[placeholder=...]` |
| 异步组件测试偶发失败 | 同一用例有时过有时不过 | 统一 `flushPromises + nextTick + setTimeout(0)` 的等待工具，所有异步断言走它 |
| 登录页 DOM wrapper 失败 | 4 个用例稳定失败 | 定位为测试环境与响应式限制；修好可修的，剩余 3 个显式 skip 并写明原因 |
| uni-app 与 Vue 版本不匹配 | H5 运行时报 `injectHook` 等错误 | 锁定依赖版本（override）+ patch 补丁，并在 postinstall 里自动应用 |
| 图片加载导致截图不稳定 | 视觉回归偶发差异 | 截图前 `waitForFunction` 等所有 img complete，再加固定等待 |
| Console 噪声太多 | E2E "无错误"用例经常误报 | 过滤 HMR / DevTools / uni-app / Vue 框架警告，只保留业务错误 |
| 思维导图渲染超时 | 内测期偶发失败 | 升级渲染库、外部 CDN 依赖本地化、调大超时；仍未彻底解决（记录为已知问题） |

## 7. 没做的测试（边界）

- **压力 / 并发测试**：没有做（内测规模小，先保证功能正确）；
- **安全渗透测试**：没有做；安全靠鉴权中间件、数据归属校验、输入校验与密钥管理这些工程约束，而不是测试证明；
- **线上监控与告警**：没有做（没有 APM、没有指标看板），出问题靠日志人工排查；
- **埋点数据验证**：没有埋点，所以留存 / 激活这类指标无法验证；
- **机型矩阵与弱网矩阵**：只做了少量真机 + 模拟弱网；
- **灰度与回滚演练**：小程序发版有小程序平台的回滚能力，但没有做过演练。

这些缺口和"止损"的结论是相关的：**没有埋点与监控，意味着即使继续做下去，也很难在合理时间内回答"用户到底有没有在用"**——这也是我当时判断"继续投入无法验证"的依据之一。
