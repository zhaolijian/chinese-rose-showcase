# 02 · 竞品调研、结论与止损判断

> 本文回答两个问题：**开工前我怎么判断"这件事值得做"**，以及**做完后我为什么判断"不值得继续做"**。两份判断的结论相反，但用的是同一套方法——这也是这个项目对我最重要的部分。
>
> 说明：当时的竞品对比表包含 40+ 款产品的截图、价格页、版本记录等第三方信息，**不随本仓库公开**。这里只保留方法、维度和结论。

---

## 1. 调研目标与方法

### 1.1 目标

在写 PRD 之前回答三件事：

1. 用户现在**怎么解决**"纸质书笔记用不起来"这个问题？
2. 我的想法里，哪些是别人已经做过的、哪些是真正没人做的？
3. 如果要做，用户**为什么**要从现有工具迁移过来？

### 1.2 方法

- **样本**：40+ 款笔记 / 书摘 / 阅读 / AI 助手类产品，全部下载安装并逐个试用核心流程；
- **信息来源**：产品内的实际操作、应用商店介绍与版本更新记录、官网公开的定价页与功能页；
- **记录方式**：一产品一行，8 个维度逐项打分——**只用三档定性**（覆盖 / 部分覆盖 / 缺失），不写"某某产品几分"这种伪精确结论；
- **不看什么**：不看营销稿里的宣传语，只以"打开产品后能不能做到"为准。

### 1.3 8 个对比维度（及为什么选它）

| # | 维度 | 看什么 | 为什么重要 |
|---|---|---|---|
| 1 | 用户与场景 | 面向谁、解决什么问题 | 判断是否与阅记正面重叠 |
| 2 | 录入方式 | 手动 / 拍照 / OCR / 导入 | 决定用户搬笔记的成本 |
| 3 | 结构化能力 | 能否按章节、主题、知识层级组织 | 阅记的核心假设所在 |
| 4 | 复习与可视化 | 是否有导图、卡片、回顾机制 | 决定"用起来"的下半段 |
| 5 | 导出与迁移 | 能否导出到通用格式、能否导入已有笔记 | 迁移成本的直接指标 |
| 6 | 商业化 | 免费 / 订阅 / 买断、定价页怎么写 | 判断品类是否被验证过付费 |
| 7 | 留存与增长设计 | 打卡、社区、推荐、模板 | 判断产品靠什么留下用户 |
| 8 | 技术壁垒与平台依赖 | OCR 来源、模型能力、生态绑定 | 判断差异化能维持多久 |

### 1.4 样本的四种类型

| 类型 | 代表产品（公开产品名） | 与阅记的关系 |
|---|---|---|
| 通用笔记 / 知识库 | Notion、Obsidian、印象笔记、飞书文档、语雀 | 能力最全，是"用户已有工具" |
| 书摘 / OCR 类 | 滴墨书摘、识墨笔记、BookxNote、Readwise 等 | 最直接的同类，决定"有没有人已经做了" |
| 阅读平台 | 微信读书、藏书馆、得到 | 有章节结构、无纸质书入口 |
| AI 助手 / Agent | Manus 类 Agent、通用对话产品 | 后来成为真正的替代者 |

## 2. 8 维对比的结论

### 2.1 定性对照（按类型，不逐产品打分）

| 维度 | 通用笔记 | 书摘 / OCR 类 | 阅读平台 | AI 助手 / Agent |
|---|---|---|---|---|
| 用户与场景 | 全场景 | 读书摘录 | 电子书阅读 | 通用任务 |
| 录入方式 | 手动 / 剪藏 | **拍照 OCR 强** | 无需录入 | 对话 / 上传 |
| 结构化能力 | 手动搭建，弱自动化 | 弱（多为平铺列表） | **章节结构强** | 弱（一次性输出） |
| 复习与可视化 | 部分（模板 / AI 摘要） | **基本缺失** | 部分（划线回顾） | 缺失 |
| 导出与迁移 | **强** | 弱（多为截图 / 图片） | 弱 | 弱 |
| 商业化 | 订阅成熟 | 订阅 / 买断 | 订阅 / 广告 | 订阅 |
| 留存与增长 | 生态与协作 | 打卡 / 社区 | 书城与社交 | 新鲜感与能力扩展 |
| 技术壁垒与平台依赖 | 数据与生态 | **低（OCR 是通用能力）** | 版权 | 模型能力 |

### 2.2 三个关键结论

1. **专做纸质书摘的产品存在，但只解决"收集"**：OCR 框选识别完就结束，不负责按章节整理，更不生成思维导图——这正是我判断的空白点；
2. **通用笔记软件覆盖了大部分能力，但缺"纸质书"这一步**：它们擅长编辑、同步、协作，不擅长从书页照片恢复结构化上下文；
3. **用户的迁移成本被严重低估**：目标用户普遍已经有印象笔记 / 飞书 / Notion，产品如果不能把笔记**导出并进入**这些体系，就只是又一个孤岛。

### 2.3 我当时的差异化假设（以及它们后来怎么样了）

| 假设 | 当时的证据 | 后来的结果 |
|---|---|---|
| ①"纸质书"是一个值得单独做的场景 | 书摘类产品只做收集、不做结构化；通用笔记不做纸质书 | **部分成立**：场景真实，但不足以支撑一个独立产品 |
| ②"结构化 + 思维导图"是差异化 | 竞品普遍缺失 | **被推翻**：导图和整理都是 AI 的通用能力，平台加一个功能就能覆盖 |
| ③"拍照到导图的极简闭环"能降低使用门槛 | 竞品流程普遍长 | **被推翻**：流程短是体验优势，不是壁垒；用户不会为"少点几步"换工具 |

## 3. 从调研到 PRD：哪些是证据，哪些是假设

| PRD 里的决策 | 依据 | 性质 |
|---|---|---|
| 支持手动 / ISBN / 扫码三种加书方式 | 竞品普遍支持，用户加书摩擦主要在"找不到书" | 有据 |
| 识别结果必须可编辑、失败要能兜底 | 试用竞品时，识别错误不可修是最大挫败点 | 有据 |
| 必须支持导出（PDF / Markdown） | 迁移成本结论的直接推论 | 有据 |
| 按章节归属笔记 | 阅读平台的章节结构是用户熟悉的心智 | 有据 |
| 用户会在复习场景持续使用 | 自己的阅读习惯 + 少量非正式交流 | **假设** |
| 导图能提升复习效率 | 学习类产品普遍提供导图 | **假设** |
| 用户愿意为结构化笔记迁移 | 无证据 | **假设（后来被证伪）** |

**这张表是后来补的。** 当时的 PRD 没有区分"证据"和"假设"——把所有内容都写得同样确定，导致开发阶段把假设当成了前提。这是我后来立项时最先改掉的习惯。

## 4. 为什么最终止损

### 4.1 时间线

```
2025.08  立项、竞品调研、PRD、原型
2025.09  核心链路开发（登录 / 书籍 / OCR / 笔记）；9 月中旬为赶节点先砍掉思维导图
2025.10  登录体验改造、设计系统统一、自动化测试补齐；导图与导出补回
2025.11–12  第二代 OCR + AI 链路（直传 + 多模态 LLM）、UI 迭代
2026.01  上线收尾
2026 上半年  上线并小范围内测 → 复盘 → 主动停止迭代
```

### 4.2 价值假设的链条断在哪

产品的完整假设链是：

```
录入成本降低 → 用户把纸质书笔记搬进来 → 在复习场景持续使用 → 留存 → 付费 / 推荐
```

内测后的判断是：

- **第一环在实现层面成立**：拍照识别 + 结构化确实把录入成本降下来了，这一点不需要用户数据也能成立——但它只是"效率更好"，不是"使用动机"；
- **第二环未验证 / 大概率不成立**：笔记是长期沉淀的数据，用户已经在别处有笔记，**没有足够理由搬到一个新工具**；导入能力又没做出来，等于把迁移门槛留在了最高点；
- **第三环无法验证**：没有规模用户、没有埋点，复习行为与留存拿不到数据；
- **第四、五环不成立**：没有用户规模，付费与推荐无从谈起。

### 4.3 真正的威胁：平台能力把差异化抹平

复盘时对比同期的通用产品：

- **Notion** 已经能做 OCR 识别、智能整理与 AI 辅助，且整理效果更好、数据与协作生态更完整；
- **Manus 这类 Agent 产品**可以把"识别 → 整理 → 导图"直接串起来，用户不需要一个专门的小程序；
- **笔记产品加 OCR 与思维导图并不难**：识别和生成都是模型能力，接入 LLM 就能做。

结论很直接：**即使我把体验做得更好，用户也没有理由从已有工具迁移过来**。继续投入只能把产品从"能用"做到"更好用"，但改变不了"没有理由换"的事实。

### 4.4 用四条止损标准逐条判断

| 标准 | 判断 | 依据 |
|---|---|---|
| 需求是否真实且高频 | ⚠️ 真实但不高频 | 读纸质书的人确实有整理需求，但"整理笔记"是低频动作 |
| 差异化是否可持续 | ❌ 不成立 | 平台能力持续吞掉工具型差异化，我没有数据 / 工作流 / 垂直 know-how 壁垒 |
| 成本结构是否成立 | ❌ 不成立 | 一个人没有低成本分发路径，获客成本决定无法验证商业假设 |
| 我是否愿意做三年 | ❌ 不愿意 | 在差异化不成立的前提下，长期投入没有复利 |

四条里三条明确不成立，按我自己定的规则，继续投入的期望值为负。

### 4.5 止损的代价

- **沉没成本**：近一年的产品与工程投入不再产生复利；
- **机会成本**：这段时间没有投入其他方向；
- **"完成了"不等于"验证了"**：这是最贵的一课——上线、内测、功能可用，都不等于价值假设被验证。

但我没有把它当"失败"处理：我把产品文档、架构、测试方法整理成这个仓库，并把判断标准带到了下一个项目。

## 5. 如果重做一次，我会怎么改

不是"下次更努力"，而是三个具体的顺序调整：

1. **先验证迁移，而不是先验证录入**。录入成本是最好验证、也最容易被 AI 抹平的一环；真正决定生死的是"用户愿不愿意把已有笔记搬过来"。做法：先做导入（Notion / 印象笔记 / 飞书）+ 导出双向打通，看用户是否真的迁移；
2. **先做服务，再做产品**。在写代码前，手工帮 10 个目标用户整理一本书的笔记（拍照 → 人工整理 → 导图），观察他们是否持续使用、是否愿意付费。这比先做 MVP 便宜一个数量级；
3. **先定"什么算验证通过"再开工**。立项时写清楚：4 周内拿到多少周活、多少用户主动推荐、多少愿意付费；拿不到就停。没有这页纸，开发进度会冒充验证进度。

另外两条产品层面的判断：

- **不要做"通用能力拼装"型产品**：OCR、AI 整理、导图生成都是平台会持续覆盖的能力；
- **要么有数据壁垒，要么有垂直 know-how，要么有工作流嵌入**——三者都没有时，先别做。

---

## 6. 可以迁移到其他项目的结论

1. **竞品调研的价值不在"看别人做了什么"，而在"确认用户现在怎么解决"**——如果现有方案已经解决了 80%，先想清楚自己的 20% 是什么；
2. **平台能力是持续变量**，做工具型产品时要假设"这个功能 12 个月后会被平台内置"；
3. **迁移成本是笔记 / 内容类产品的第一道生死线**，比功能数量重要。
