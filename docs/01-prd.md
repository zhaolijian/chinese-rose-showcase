# 01 · 核心 PRD：阅记 MVP 的产品定义

> 本文基于当时的 PRD v1.0（2025-08）改写。改写原则：**删掉未实现的承诺、把假设标注为假设、把验收标准补上"实际结果"**。原文中"业内首创""端到端加密""10 万 MAU 数据预估"等表述不进入本仓库——前两者没有验证 / 没有实现，后者没有依据。

---

## 1. 目标用户与场景假设

### 1.1 三个用户画像（假设，非访谈结论）

| 画像 | 特征 | 核心痛点 | 典型场景 |
|---|---|---|---|
| 知识型职场人 | 28 岁左右，每月 2–3 本专业书，习惯在书上划线 | 笔记难检索、读完就忘、无法形成体系 | 通勤时回顾昨晚的笔记；周末整理一周阅读；分享会前导出导图 |
| 备考学生 | 教材 / 参考书密集标注，需要反复复习 | 笔记分散在各本书里，复习效率低 | 课后拍照保存重点；考前用导图串联知识点；导出 PDF 打印 |
| 重度读者 / 写作者 | 月读多本，有写书评 / 找素材的习惯 | 多年笔记缺乏整理，写作时找不到素材 | 随时记录金句；按主题检索；用导图搭书评大纲 |

**方法说明**：这三个画像来自竞品使用观察 + 自身阅读习惯的归纳，**不是正式用户访谈的产物**。当时的验证方式是"先做出可用的版本，再用内测反馈修正"；事实证明这个顺序有问题——真正应该先验证的是"用户是否愿意为结构化笔记迁移工具"（见 [02-research-and-decision](./02-research-and-decision.md)）。

### 1.2 问题定义：三个断点

1. **录入成本高**：手抄划线句太慢；拍照后逐条整理更麻烦；
2. **结构缺失**：划线句是碎片，不知道属于哪一章、在书里的什么位置；
3. **无法迁移**：整理好的笔记留在某个 App 里，进不了用户已有的笔记体系。

产品假设：如果能把"拍照 → 结构化笔记"的成本压到接近零，用户就会把纸质书笔记搬进来，并在复习场景持续使用。

### 1.3 用户旅程（当时的定义）

```
发现（朋友分享 / 搜索）→ 首次使用（不强制登录，先看书架）
→ 核心体验（添加书 → 拍照识别 → 保存笔记）
→ 深度使用（按章节整理、生成导图、导出）
→ 传播（分享导图 / 推荐）
```

关键体验决策：**首次进入不强制登录**，用户可以先浏览书架（空态 + 引导），在真正需要写入数据时才要求登录。这一条是后来 ADR-007「先体验后登录」的前身。

## 2. 四个 MVP 核心功能

原始需求列表 30+ 条，最终只保留 4 个核心功能。它们共同构成一条完整链路：

```
① 书籍与笔记管理 → ② 拍照识别与结构化整理 → ③ 阅读与编辑（含导出）→ ④ 思维导图
```

### 2.1 功能一：书籍与笔记管理

- **用户故事**：作为读者，我希望快速把正在读的书加入书架，并按书管理笔记。
- **能力范围**：书架列表（笔记数量统计、最近更新排序）、手动添加、ISBN 查询自动补全、扫码输入 ISBN、删除（有笔记 / 导图时禁止删除）、笔记列表（按时间排序）。
- **关键规则**：
  - 书籍必填只有书名，作者 / 出版社 / ISBN / 封面均选填——降低首次录入摩擦；
  - ISBN 查询失败时自动降级为手动填写，不阻断流程；
  - 删除书籍不级联删除笔记：有笔记或导图时不允许删书，必须先把关联内容处理掉——这是内测用户明确反馈"不想删书顺手把笔记也删了"之后改的规则。
- **实际状态**：✅ 已完成并在内测中使用。

### 2.2 功能二：拍照识别与结构化整理

- **用户故事**：作为读者，我希望拍下书页、框选划线句，系统把它识别成文字，并整理成能读懂的句子。
- **能力范围**：拍照 / 相册选图、单次多区域框选、图片压缩、OCR 识别、识别结果可编辑、按章节归属、保存为笔记。
- **关键规则（这个功能的难点都在规则里）**：
  1. **划线句经常是半句**：直接提取会得到语义断裂的碎片。处理规则是——在不改变原意的前提下，参考相邻划线句或上下文，把碎片整理成逻辑通顺的句子，并去掉"我 / 你"这类个人指向性表述；
  2. **整理要有结构，但不能变成小作文**：按「结论先行、以上统下、归类分组、逻辑递进」做一层结构化，不做多层嵌套；
  3. **要知道这句话在书里的位置**：设计上用三重信息定位——书籍目录（章节标题）、拍照页边角的当前章信息、页码；
  4. **识别失败必须能兜底**：降级为手动输入 / 手动框选重试，不允许把用户卡死在错误页。
- **实际状态**：✅ 主链路已完成并内测；⚠️ 章节的**自动**解析未完成（作品目录 / 页边章节的自动识别没做出来），内测期章节归属依赖用户选择与手动确认。

### 2.3 功能三：阅读与编辑（含导出）

- **用户故事**：作为读者，我希望在一个沉浸式环境里连续回顾某本书的笔记，并能把笔记导出到别处使用。
- **能力范围**：阅读模式（卡片流、连续滑动）、编辑模式（单条笔记修改）、模式切换自动保存；单条笔记导出 PDF / Word / Markdown。
- **关键规则**：编辑与阅读是两个明确状态，切换时自动保存；导出优先保证"能进入用户已有工具"，所以 Markdown 带标题层级与元信息，PDF 保持可打印排版。
- **实际状态**：✅ 阅读 / 编辑 / 导出均可用；导出实测：单条笔记 PDF 生成约 0.75s（2025-09-07 的接口级测试记录，不含网络传输）。

### 2.4 功能四：思维导图生成

- **用户故事**：作为读者，我希望系统把这本书的笔记整理成一张思维导图，帮我快速回顾知识结构。
- **能力范围**：基于某本书的笔记自动生成导图、查看（缩放）、保存图片到相册、删除。
- **关键规则**：
  - 导图**只有一层结构**（主题 → 一级分支 → 二三级要点），不做无限嵌套——避免把笔记变成"目录树"；
  - 生成以"书"为单位，笔记按创建时间顺序作为上下文输入；
  - 允许重新生成；生成失败时保留原图，不覆盖历史结果。
- **实际状态**：✅ 主链路可用，生成的导图可保存到相册；⚠️ 渲染链路的稳定性是当时的薄弱点（内测期偶发超时 / 渲染失败，后期通过更换渲染库、把外部 CDN 依赖本地化、调整超时配置缓解，但没有做到 100% 稳定）。

### 2.5 明确"不做"的清单

| 被砍掉的需求 | 处理 | 理由 |
|---|---|---|
| 社交分享 / 读书社区 | 不做 | 与"个人知识结构"的价值无关，且冷启动需要内容供给，一个人做不了 |
| App 端（iOS / Android） | 不做，只留配置 | 多端是一码多端的方向，但这个阶段没有验证完小程序，做 App 是分散资源 |
| 多端同步 / 账号体系打通 | 不做 | 单端足够验证核心链路；只保留了"按时间增量拉取笔记"的简单接口，没有做真正的多端同步机制 |
| 协作批注 / 共享笔记 | 不做 | 纸质书笔记是强个人场景，没有证据表明需要协作 |
| 标签体系 / 主题筛选 | 推后 | 优先级低于"章节结构"，且标签会增加录入成本 |
| 数据分析看板（阅读量 / 笔记量趋势） | 不做 | 对内测用户没有价值，对我也只是"看起来专业" |
| 付费 / 会员 | 不做 | 无用户规模时验证定价没有意义，先把价值假设验证清楚 |
| 多语言 / 自定义字体 / 夜间模式 | 推后 | 纯体验增强，不影响核心闭环 |
| 笔记问答（RAG） | 不在 MVP | 有价值但成本高（检索 + 向量库 + 评测），在核心价值未验证前不做 |
| "导入已有笔记"（印象笔记 / 飞书 / Notion 等） | 只做规划、未实现 | 它承担"降低迁移成本"的关键作用，但实现成本高；这是当时判断里的一个缺口（见 02） |

## 3. 30+ 需求如何收敛到 4 个功能

### 3.1 收敛方法：三问 + 三分类

对每条需求问三个问题：

1. 它是否直接支撑核心闭环（拍照 → 结构化 → 复习）？
2. 它是否可以被用户已有的工具替代（不需要自己做）？
3. 它是否有可验证的验收标准（做了之后怎么算成功）？

然后据此分类：

| 分类 | 判定标准 | 处理 |
|---|---|---|
| P0 · 保留 | 直接支撑核心闭环，且没有它闭环走不通 | 进入 MVP，写验收标准 |
| P1 · 推后 | 增强体验但不影响闭环，成本可控 | 记录在需求池，不进入 MVP |
| 不做 | 与核心价值无关、或无法验证收益 | 明确写"不做"及理由，避免反复讨论 |

### 3.2 从 7 条 P0 用户故事到 4 个功能

当时的 P0 用户故事有 7 条（注册引导、加书、拍照识别、纠错、连续阅读、生成导图、导出），工作量为相对点数的加总。它们被归并成 4 个功能模块，原因是：**用户故事是验收单位，功能模块是开发单位**——如果按 7 条故事平行开发，会得到 7 个半成品；归并后每个模块都能独立交付、独立验收。

### 3.3 范围不是一次收敛的：思维导图被砍掉又加回来

真实的收敛过程不是"一次想清楚 4 个功能"，而是**砍了再加**：

- 9 月中旬，为了赶 10 月 1 日的上线节点，我先把思维导图整个砍掉，只保留"登录 + 书籍 + OCR + 笔记"——当时的判断是"导图是加分项，不是主干"；
- 做完 OCR 与笔记之后发现：如果笔记只是"识别出来的文字列表"，它和市面上的书摘工具没有区别；**用户真正需要的是"结构"**，而导图是结构最直观的呈现方式。于是 10 月又把导图加回来，并把它作为核心闭环的一环；
- 加回来的代价是进度后移，也说明第一次砍的时候对"核心价值"的判断不够准——我用"能不能上线"代替了"什么才是差异化"。

这一段后来被我写进了复盘：**砍需求时要砍"不影响验证假设的功能"，而不是砍"实现成本高的功能"**。思维导图恰恰是验证"结构化价值"的关键，它不该被成本逻辑砍掉。

### 3.4 收敛的代价

- 产品在竞品对比里"看起来薄"：没有社区、没有多端、没有会员；
- 增长缺少抓手：没有分享裂变、没有内容外链，获客只能靠人工邀请；
- 部分被推后的需求（导入）后来被证明很关键——**它直接决定用户迁移成本**，见 02 的复盘。

## 4. 验收标准与实际达成

### 4.1 功能验收

| 验收项 | 当时目标 | 实际结果 |
|---|---|---|
| 核心流程可完整走通 | 拍照 / 框选 → 识别 → 结构化笔记 → 导图 → 导出 | ✅ 走通 |
| 书籍添加 | 手动 / ISBN / 扫码三种方式 | ✅ 可用；ISBN 查询失败自动降级手动 |
| OCR 识别 | 印刷体识别准确率 > 95%（目标值） | ⚠️ **未系统测量**；内测体感"多数可用、需要手动纠错"，无量化数据 |
| 识别失败兜底 | 有友好提示与重试 / 手动输入 | ✅ 有降级路径 |
| 章节归属 | 按目录 / 页边 / 页码三重定位 | ⚠️ 数据模型与手动归属已落地；自动解析未完成 |
| 阅读 / 编辑 | 双模式切换自动保存 | ✅ 可用 |
| 导出 | 单条笔记导出 PDF / Word / Markdown | ✅ 可用（PDF 接口级测试通过） |
| 思维导图 | 基于笔记生成、可查看、可保存 | ✅ 可用；⚠️ 渲染稳定性未达标 |

### 4.2 性能验收（诚实版）

| 指标 | 当时目标 | 实际情况 |
|---|---|---|
| 单页 OCR 处理 | < 3 秒 | ⚠️ 未做端到端基线；"上传 + 多模态模型识别"链路在弱网下明显超过 3 秒 |
| 页面切换 | < 500ms | ⚠️ 未系统测量（无性能埋点） |
| 书架加载 | < 1 秒（50 本书内） | ⚠️ 未系统测量 |
| 导图生成 | < 5 秒 | ⚠️ 未稳定达标；渲染链路存在偶发超时 |
| 导出生成 | < 2 秒 | ✅ 接口级记录：单条笔记 PDF 约 0.75s（不含下载时间） |

### 4.3 体验验收

- ✅ 空态 / 加载态 / 错误态有统一组件（骨架屏、空态、友好错误提示）；
- ✅ 未登录可先浏览书架，写入操作才引导登录；
- ⚠️ 新手引导只有空态文案，没有分步引导（成本取舍：优先级低于核心链路）；
- ⚠️ 识别结果的可编辑性可用，但"整体格式化 / 二次整理"的体验一般（依赖模型输出质量）。

### 4.4 非功能要求（修正后的口径）

- **安全**：HTTPS 传输、JWT 鉴权（7 天有效期）、用户数据按账号隔离、手机号 AES 加密存储、日志脱敏、对象存储用预签名 URL 直传（后端不接触长期密钥下发）；
- **隐私**：OCR 图片写入对象存储临时目录，识别完成后可由前端删除；**没有实现端到端加密**，也不承诺"图片绝不出端"；
- **兼容性**：真机只覆盖了少量 iPhone / Android 设备，没有做机型矩阵兼容测试；
- **可维护性**：Go 侧单元测试与集成测试、前端单测与 E2E 已建立，但整体覆盖率未达到 80% 目标（见 [05-testing-and-quality](./05-testing-and-quality.md)）。

## 5. 这份 PRD 现在回看的问题

1. **指标写得太漂亮**：留存、转化、NPS 目标在"没有埋点、没有规模用户"的现实下没有意义，不如写"验证问题 + 止损标准"；
2. **把假设写成了结论**：画像、迁移意愿、复习效率提升都是假设，PRD 里没有标注，导致开发阶段把它们当成了已验证的前提；
3. **性能目标没有测量方案**：写了 < 3s / < 500ms，但没有定义怎么测、在什么网络环境下测，最后无法验收——**没有测量方案的目标等于没有目标**；
4. **导入被推后是判断失误**：它直接决定"用户能否把已有笔记搬过来"，应该至少做一个可用版本来验证迁移意愿。

这四条后来被我写进了下一个项目的立项检查清单。
